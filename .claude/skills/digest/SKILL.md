# デイリーダイジェストを作る

X・YouTube・Steam で伸びた投稿から記事 `src/content/posts/daily-digest/<date>.md` を作る。
**載せるかどうかを決めるのは人間**。Claude は候補を整理して提案し、指示どおりにルールや選定を直す。黙って候補を落とさない。

候補は**実行時点から直近24時間**の投稿・動画（`config.yaml` の `collect.windowHours`）。`<date>` は記事の日付で、今日（JST）。
引数に日付（YYYY-MM-DD）があれば、その日の作りかけの記事（保存済みの候補・選定）の続きを扱う。その場合 collect は実行しない（今日以外の日付では収集できない）。
コマンドはすべてリポジトリのルートで `pnpm -s digest <コマンド> --date <date>` として実行する。

## 1. 候補を集める

```sh
pnpm -s digest collect --date <date>
```

- X の読み取りは従量課金。保存済み（`.digest-cache/<date>/candidates.json`）なら取り直さないので、そのまま進む。
- `--force` で取り直すのは、ユーザーが明示的に頼んだときだけ。
- 同じ日に2回目を実行しても、保存済みの候補（1回目の実行から24時間分）を使う。最新の24時間で取り直したいときは `--force`。
- 前日の記事と期間が重なる投稿は、掲載済みなら自動で候補から外れる。

## 2. 候補を見せる

```sh
pnpm -s digest review --date <date>
```

- 出力と `.digest-cache/<date>/shortlist.json`（本文・共有者などの詳細）を読む。
- `scripts/daily-digest/selection-guide.md` の選定基準を読み、それに沿った**おすすめ**を用意する。
- ユーザーには次の形で見せる。すべてを貼らず、カテゴリごとに短くまとめる。
  - カテゴリ／区切りごとに `#番号 一行要約（主な数値）`
  - 載せたい候補には ✅ を付ける。
  - 基準に引っかかる候補には ⚠️ と理由を付ける（炎上・懸賞・AIイラスト・性的な内容への言及など）。**勝手に除外せず、判断はユーザーに任せる**。
  - 収集エラーや、候補が少ないカテゴリがあれば書く。
- 最後に、ルールにしてよさそうなものを提案する（例:「#12 の投稿者は懸賞ばかりなので block しますか？」）。

## 3. 指示を反映する

ユーザーの指示を、**今後も効くもの**と**今回だけのもの**に分けて扱う。

| ユーザーの言い方の例 | やること |
|---|---|
| 「#3 の人ブロック」「このチャンネル今後いらない」 | `curate block author:#3 --reason <理由>` |
| 「#5 はもう出さないで」 | `curate block '#5' --reason <理由>` |
| 「VTuber 少し強めに」「AI の話題は控えめに」 | `curate weight genre:vtuber 1.5 --reason <理由>`（強めは 1.5〜2、控えめは 0.5 前後から） |
| 「この人の曲は優先して」 | `curate weight author:#7 2 --reason <理由>` |
| 「#9 は絶対入れて」「推し」 | `curate pin '#9' --reason <理由>` に加え、選定にも入れる |
| 「@xxx は bot なので共有者から外して」 | `curate ignore-sharer @xxx --reason <理由>` |
| 「懸賞っぽい投稿は下げて」 | `curate weight 'text:フォロー.?RT' 0.3 --reason <理由>`（text は正規表現） |
| 「今月だけ」 | どのルールにも `--until YYYY-MM-DD` を付ける |
| 「さっきのルール取り消して」 | `curate unset <同じ対象>`（`curate list` で確認できる） |
| 「#4 は今回は外して」「#6 と差し替え」 | ルールにはせず、選定（selection.json）だけを直す |

- ルールにするか今回だけにするか分からないときは、ユーザーに聞く。
- `--reason` には、ユーザーの言葉を短くまとめて入れる。
- ルールを変えたら `review` をやり直し、並びや除外がどう変わったかを短く伝える。番号は同じ日のうちは変わらない。
- `review --all` を使うと、除外された候補と圏外の候補も見られる。

## 4. 選定して記事にする

`.digest-cache/<date>/selection.json` を次の形で書き、`render` を実行する。

```json
{
  "topic": "記事タイトルの前半（40文字以内、日付なし）",
  "topicKey": "#8",
  "description": "記事全体の1文紹介（80文字以内）",
  "items": [{ "key": "#8", "note": "" }, { "key": "#2", "note": "性的な内容への言及あり" }]
}
```

```sh
pnpm -s digest render --date <date>
```

- `key` と `topicKey` は `#番号` でも `youtube:xxx` でもよい。
- 件数とカテゴリごとの上限は `config.yaml` の `article` に従う（`review` の見出しにも上限が出る）。上限を超えた項目は render が外して警告する。
- topic と description は `selection-guide.md` の「書き方」に従う。
- render の警告（除外済みの項目・上限超え・note）はユーザーに伝える。
- プレビュー: `pnpm dev` がまだ動いていなければバックグラウンドで起動し、render が出す URL を伝える。

## 5. 添削する

- 「タイトルを変えて」「説明を短く」: selection.json の `topic` / `description` を直して `render` し直す。
- 項目の追加・削除・差し替え: selection.json の `items` を直して `render` し直す。
- 記事の .md は `render` で上書きされるので、直接は編集しない。

## 6. 公開する

公開の前に、次の点を確認してユーザーに報告する。

- [ ] タイトル・説明が掲載内容と食い違っていない。煽りすぎていない
- [ ] 政治・事件・炎上・個人を晒す内容が含まれていない
- [ ] note に ⚠️ が付いた項目（性的な内容への言及など）を載せるか、ユーザーが判断した
- [ ] 自己啓発系の名言は出典が確かである
- [ ] プレビューで埋め込みが正しく表示される（ユーザーに確認してもらう）

**ユーザーが「公開して」「OK」とはっきり言ったときだけ**次を実行する。

```sh
pnpm -s digest publish --date <date>
```

- develop ブランチ（または `digest/<date>`）で実行する。ほかのブランチにいるときは、切り替えてよいかユーザーに聞く。
- 実行する内容: `pnpm build` → develop を pull → `digest/<date>` ブランチを作る → 記事と curation.yaml をコミット → push → PR 作成 → CI を待ってマージ → develop に戻る。
- マージせず PR だけ作るときは `--no-merge` を付ける。
- 終わったら PR の URL と、develop へのデプロイで公開されることを伝える。
